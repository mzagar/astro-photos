# AGENTS.md — working notes

Operating instructions for whoever maintains this gallery (agent or human).
`README.md` is for visitors; this file is for editing the site.

## Ground rules

- **Visitor-facing copy is English**, including photo titles and captions.
- **Only watermarked, AI-enhanced exports are published.** They come from the
  Seestar app's share/export; the watermark (owner, location, time, object,
  integration) is part of the picture and is never cropped away.
- `masters/` and `raw/` are gitignored and must stay out of git. `masters/` holds
  the published exports, `raw/` holds earlier non-watermarked stacks.
- Keep the site dependency-free: no frameworks, no bundler, no external fonts or
  CDNs. One HTML file, one generated data file, JPEGs.

## Data model

`gallery-data.js` is generated by `scripts/build_gallery.py` as
`window.GALLERY_DATA = { site, photos[] }`. Each photo entry:

| field | meaning |
|---|---|
| `file`, `thumb` | paths under `photos/` |
| `title`, `caption` | hand-written, English |
| `date` | capture date, `YYYY-MM-DD`, taken from the filename |
| `time` | optional capture time `HH:MM`, hand-written, only used for ordering |
| `group` | object slug; photos sharing it become one tile |
| `integration` | minutes (float) or `null` |
| `variant` | label such as `crop`, `wide`, `boosted`, `stacked`, `2x` |
| `width`, `height` | thumbnail size, used to reserve space in the grid |

The build preserves `title`, `date`, `time` and `caption` **keyed by `file`**.
Renaming a master changes the slug, so those hand-written values are lost — retype
them after a rename.

## Filename convention

`YYYY-MM-DD_object[-<minutes>m[-<label>] | --<label>].jpg`

| name | group | integration | variant |
|---|---|---|---|
| `2026-11-14_m31-andromeda-36m.jpg` | `m31-andromeda` | 36 | — |
| `2026-11-14_m31-andromeda-36m-boosted.jpg` | `m31-andromeda` | 36 | `boosted` |
| `2026-11-19_ic434-horsehead-22m-crop.jpg` | `ic434-horsehead` | 22 | `crop` |
| `2026-11-18_moon--2x.jpg` | `moon` | — | `2x` |
| `2026-11-16_m33-triangulum-45m.jpg` | `m33-triangulum` | 45 | — |

- A single dash before the time stamp is the integration; a trailing label after
  it separates versions of the same length.
- A double dash adds a label **without** an integration time (zoom levels,
  processing variants).
- Sources smaller than the target size are never upscaled.

## Grouping and ordering

- One tile per `group`, regardless of capture date.
- Variants are sorted by integration descending, then an unlabelled version first,
  then by label (numeric-aware, so `2x` precedes `10x`). The first variant is the
  **cover**: its thumbnail, title, date and time represent the tile.
- Tiles are ordered **newest first** by the cover's `date` + `time`. A new version
  of an existing object therefore stays at its chronological position; only a new
  object moves to the top left.
- Chips inside the lightbox read `formatIntegration(integration) · variant`, e.g.
  `36 min · boosted`, or just the label when there is no integration time.

## Adding a photo

1. Copy the export into `masters/` using the naming rules above.
2. `python3 scripts/build_gallery.py`
3. In `gallery-data.js`, set `title`, `time` and `caption`. Keep captions factual:
   integration, framing/AI note, capture time. No em dashes — use commas.
4. `node scripts/check_site.js`
5. `./publish.sh "Add <object>"`
6. Verify the deployment (see below) before claiming it is live.

## Publishing

The repository is `mzagar/astro-photos`, public, with GitHub Pages serving `main`
from the repository root. `publish.sh` builds, commits and pushes; Pages rebuilds
in about a minute.

```bash
gh auth status                       # must be logged in as mzagar
./publish.sh "Add M33, Triangulum"
```

Verification, in this order:

```bash
gh api repos/mzagar/astro-photos/pages/builds/latest --jq '.status + " " + .commit'
git rev-parse HEAD
```

**Gotcha:** `pages/builds/latest` may still report the *previous* build as `built`.
Compare the reported `.commit` with `HEAD` and only accept `built <HEAD>`; then
`curl` the live page and each new image and expect `200`. Add a cache-busting
query when grepping the HTML.

## Code notes

- The grid is CSS Grid masonry: `grid-auto-rows: 6px` and a per-card
  `grid-row: span N` computed in `layout()` from the thumbnail aspect ratio plus a
  12 px gap. `layout()` re-runs on resize. DOM order equals visual order.
- Captions are overlaid on the picture (top-to-bottom gradient) so a tile's height
  is exactly its image height — that keeps the masonry maths simple.
- Lightbox: full-size image, metadata, and `Exposures` chips that swap the image in
  place. Arrow keys step between objects and reset to the cover.
- Zoom overlay: wheel/pinch zoom, drag to pan, double tap for 1×/2.5×, `+`/`-`/`0`,
  `Esc`. `Esc` closes zoom first, then the lightbox.
- `scripts/check_site.js` mounts the real inline script against a hand-written DOM
  shim and asserts ~70 behaviours, including data-driven ordering. It needs no
  browser and no dependencies; run it before every publish.

## Gotchas

- `sips` is macOS-only; the build fails elsewhere.
- `__pycache__/` and `*.pyc` are gitignored — do not commit them.
- Deleting a master leaves an orphan JPEG in `photos/`; the build prints a note
  but does not remove it.
- The site is public and the images are watermarked: do not publish files that
  still contain EXIF metadata you would not want shared.
